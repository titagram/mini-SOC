🤖 Insecure CAPTCHA

Bypassare implementazioni insicure dei sistemi CAPTCHA

📖 Cos'è un CAPTCHA?

Definizione

CAPTCHA (Completely Automated Public Turing test to tell Computers and Humans Apart) è un sistema di challenge-response usato per determinare se l'utente è umano o un bot automatizzato.

Lo scopo è prevenire:

  • 🤖 Bot automatizzati
  • 📧 Spam
  • 🔓 Attacchi brute force
  • 🎟️ Ticket scalping e scraping

CAPTCHA Sicuro vs Insicuro

✅ CAPTCHA Sicuro

Validazione server-side
Token crittografati
Challenge imprevedibili

❌ CAPTCHA Insicuro

Validazione client-side
Parametri predicibili
Logica bypassabile

Low Security Vulnerabilità e Sfruttamento

⚠️ Vulnerabilità: Il processo di validazione è suddiviso in 2 step. Un attaccante può bypassare lo Step 1 (CAPTCHA) modificando direttamente il parametro step.

Logica Vulnerabile:

Step 1: Verifica input e CAPTCHA

Step 2: Se Step 1 ha successo, mostra pulsante "Submit" per completare

Il problema: non c'è una reale connessione tra i due step sul server!

🎯 Bypass: Manipolazione Parametro Step

Procedura con Burp Suite:

  1. Configurare Burp Suite per intercettare il traffico
  2. Tentare un cambio password (verrà mostrato il CAPTCHA)
  3. Intercettare la richiesta HTTP
  4. Modificare il parametro step da 1 a 2: 
    step=2&password_new=hacked&password_conf=hacked
  5. Inoltrare la richiesta modificata

💡 Perché Funziona:

Il server si aspetta che step=2 venga inviato SOLO dopo aver completato step=1 (con CAPTCHA risolto). Tuttavia, non c'è verifica server-side che lo step 1 sia effettivamente stato completato!

Saltando direttamente a step=2, bypassiamo completamente il CAPTCHA.

Lezione: La validazione multi-step deve essere gestita correttamente sul server con session state.

Medium Security Protezioni Implementate

🛡️ Nuova Difesa: Il sistema verifica un parametro passed_captcha per determinare se il CAPTCHA è stato superato.

Logica di Validazione (Concettuale):

if ($_POST['step'] == 2) {
    if ($_POST['passed_captcha'] == 'true') {
        // Cambia password
    } else {
        die('CAPTCHA verification failed');
    }
}

🎯 Bypass: Manipolazione Parametro passed_captcha

Il parametro passed_captcha è controllato sul lato client e può essere facilmente manipolato.

Procedura con Burp Suite:

  1. Intercettare la richiesta di cambio password
  2. Modificare i parametri: 
    step=2&passed_captcha=true&password_new=hacked&password_conf=hacked
  3. Inoltrare la richiesta

💡 Problema Fondamentale:

Il server si fida del parametro passed_captcha inviato dal client. Un attaccante può semplicemente impostarlo a true senza mai risolvere il CAPTCHA!

Lezione: Mai fidarsi dei dati provenienti dal client. La validazione DEVE avvenire completamente sul server.

High Security Protezioni Avanzate

🛡️ Difese Implementate: Validazione a più strati con fallback che richiede header User-Agent specifico e valore nascosto.

Logica di Validazione (Concettuale):

// Prima verifica reCAPTCHA reale
if (!verifica_recaptcha($_POST['g-recaptcha-response'])) {
    // Fallback: controlla valore nascosto
    if ($_POST['g-recaptcha-response'] != 'hidd3n_valu3' || 
        $_SERVER['HTTP_USER_AGENT'] != 'reCAPTCHA') {
        die('CAPTCHA failed');
    }
}
// Procedi con cambio password

🎯 Bypass: Header Manipulation

Procedura con Burp Suite:

  1. Intercettare la richiesta POST
  2. Modificare i parametri e gli header: 
    POST /vulnerabilities/captcha/ HTTP/1.1
...
User-Agent: reCAPTCHA

step=2&g-recaptcha-response=hidd3n_valu3&password_new=hacked&password_conf=hacked
  3. Inoltrare la richiesta modificata

💡 Analisi della Vulnerabilità:

Il codice ha una logica di fallback che accetta valori hardcoded (hidd3n_valu3 e User-Agent reCAPTCHA). Questo è probabilmente codice di debug lasciato per sbaglio in produzione!

Un attaccante che analizza il codice sorgente (o fa reverse engineering) può scoprire questi valori magici e bypassare completamente il CAPTCHA.

Lezioni:

  • Mai lasciare backdoor o codice di debug in produzione
  • Non hardcodare valori segreti nel codice client-visible
  • Usare configurazione separata per dev/prod

Impossible Implementazione Sicura

✅ Difese Implementate:
  • stripslashes() per pulizia input
  • Token Anti-CSRF generato per ogni richiesta
  • Prepared statements per query SQL
  • Processo semplificato in un unico step
  • Validazione server-side completa

Approccio Sicuro (Concettuale):

// Verifica token anti-CSRF
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    die('CSRF token invalid');
}

// Verifica reCAPTCHA con Google API
$recaptcha_response = $_POST['g-recaptcha-response'];
$recaptcha_secret = 'YOUR_SECRET_KEY';
$response = file_get_contents(
    "https://www.google.com/recaptcha/api/siteverify?secret=" . 
    $recaptcha_secret . "&response=" . $recaptcha_response
);
$response_data = json_decode($response);

if (!$response_data->success) {
    die('reCAPTCHA verification failed');
}

// Solo ora procedi con il cambio password
// usando prepared statements
$stmt = $pdo->prepare("UPDATE users SET password = ? WHERE username = ?");
$stmt->execute([hash_password($new_password), $username]);

💡 Perché è Sicuro:

  • ✅ Validazione reCAPTCHA reale: Chiamata API a Google per verificare il token
  • ✅ Token Anti-CSRF: Previene replay attacks
  • ✅ Unico step: Elimina problemi di state management multi-step
  • ✅ Server-side only: Nessuna decisione basata su input client
  • ✅ Prepared statements: Previene SQL injection

Risultato: Non ci sono bypass noti. Il sistema richiede genuina interazione umana e validazione crittografica robusta.

🛡️ Strategie di Mitigazione

1. Usare reCAPTCHA di Google (v2/v3)

  • reCAPTCHA v2: Checkbox "I'm not a robot" con challenge visivi
  • reCAPTCHA v3: Score-based, invisibile all'utente
  • Validazione server-side: Sempre verificare con API Google
  • Secret key sicura: Mai esporre la chiave segreta al client

Implementazione Corretta (PHP):

$recaptcha_secret = getenv('RECAPTCHA_SECRET_KEY');
$response = $_POST['g-recaptcha-response'];

$verify = file_get_contents(
    'https://www.google.com/recaptcha/api/siteverify?' . 
    http_build_query([
        'secret' => $recaptcha_secret,
        'response' => $response,
        'remoteip' => $_SERVER['REMOTE_ADDR']
    ])
);

$captcha_success = json_decode($verify);
if ($captcha_success->success && $captcha_success->score > 0.5) {
    // Procedi
} else {
    // Blocca
}

2. Validazione Server-Side Completa

  • Mai fidarsi di parametri client-side (passed_captcha, etc.)
  • Sempre validare con API del provider CAPTCHA
  • Verificare timeout del token CAPTCHA
  • Token monouso (non permettere riuso)

3. Session State Management

  • Memorizzare stato CAPTCHA nella sessione server
  • Verificare che il CAPTCHA sia stato completato prima di procedere
  • Invalidare token dopo l'uso
  • Timeout sessione appropriato
// Dopo verifica CAPTCHA successo
$_SESSION['captcha_verified'] = true;
$_SESSION['captcha_timestamp'] = time();

// Prima di eseguire azione protetta
if (!isset($_SESSION['captcha_verified']) || 
    time() - $_SESSION['captcha_timestamp'] > 300) {
    die('CAPTCHA expired or not verified');
}

// Invalida dopo uso
unset($_SESSION['captcha_verified']);

4. Alternative a CAPTCHA Tradizionale

  • hCaptcha: Alternative open-source a reCAPTCHA
  • Cloudflare Turnstile: CAPTCHA invisible privacy-focused
  • Honeypot fields: Campi nascosti che i bot compilano
  • Rate limiting: Limitare tentativi per IP/sessione
  • Behavioral analysis: Analisi del comportamento utente (mouse movement, keystroke dynamics)

5. Defense in Depth

  • CAPTCHA + Rate limiting + Account lockout
  • CAPTCHA + Anti-CSRF tokens
  • Progressive challenges (CAPTCHA dopo N tentativi falliti)
  • Risk-based challenge (CAPTCHA per IP/comportamenti sospetti)

6. Monitoring e Logging

  • Loggare tutti i tentativi CAPTCHA (successi e fallimenti)
  • Alert su pattern sospetti (troppi fallimenti, bypass attempts)
  • Analisi statistica per rilevare bot
  • Blacklisting IP con comportamento malevolo

7. Best Practices Implementazione

  • ❌ Non usare CAPTCHA hardcoded o predicibili
  • ❌ Non fare validazione solo client-side
  • ❌ Non lasciare backdoor di debug in produzione
  • ✅ Usare librerie ufficiali (reCAPTCHA, hCaptcha)
  • ✅ Sempre validare server-side con API del provider
  • ✅ Combinare con altre tecniche di sicurezza

📌 Riepilogo

I CAPTCHA insicuri possono essere bypassati tramite manipolazione parametri, header spoofing, o sfruttamento di logica debole. La difesa richiede validazione server-side con API del provider CAPTCHA, session state management corretto, e combinazione con altre tecniche anti-bot.

Regola d'oro: Mai fidarsi del client. Validare sempre lato server.
